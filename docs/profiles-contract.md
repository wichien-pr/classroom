# Account profiles — contract

## Profile card and editor
- `/account/profile` is a read-only card with an edit link. `/account/profile/edit` contains separate, non-nested text, photo-upload and photo-removal forms, with local preview and photo feedback. Its text endpoint (GET/POST) edits **only** the session owner's display name, username and plain-text bio. A separate endpoint keeps text edits under the existing 16 KiB request limit; it cannot alter photos, email, password, IDs or timestamps. Exact fields: `csrf_token`, `name`, `username`, `bio`; duplicate/unknown fields and files are rejected. Existing session CSRF, Origin and Sec-Fetch-Site checks apply. Success redirects 303; validation is 400; username collision is 409 with safe entered fields retained.
- Name: trim, 1–80 Unicode code points; no ASCII C0 control characters. Bio: trim, 0–500 Unicode code points; line breaks/tabs allowed, other ASCII C0 controls rejected. Jinja autoescaping is retained: HTML is displayed as text, never rendered. Browser maxlength is an early convenience; server validation is authoritative.
- Username: trim, lowercase ASCII, `[a-z0-9][a-z0-9_-]{2,31}`; 3–32 characters. The `@` is a UI prefix, **not stored** and not entered in the field. Case-insensitive unique SQLite index makes concurrent collisions deterministic (409). `member-<digits>` is reserved; only the owning ID may use its exact default. This prevents future registrations colliding with user-selected reserved handles.
- Additive fields: `username TEXT`, `bio TEXT NOT NULL DEFAULT ''`, `joined_at REAL NULL`, `last_active_at REAL NULL`. Existing accounts receive stable `member-<id>` handles, not a derivation of email/name. An AFTER INSERT trigger supplies the same default when no handle is provided. No existing name/email/password/photo/progress/exam/session data is reset.
- **Legacy joined dates remain NULL.** They cannot be reconstructed and render `ไม่ทราบวันที่สมัคร`. New `/register` requests write actual server UTC Unix seconds at insertion. There is no fabricated migration-date registration date. Last activity also starts NULL until a qualifying authenticated request.
- Successful authenticated Classroom/profile/member/leaderboard/exam page and progress/exam API requests record server UTC activity, at most once per account per 60 seconds (conditional SQL plus pre-check). Anonymous, invalid/failed requests, photo loads, course assets, static files, and passive open tabs do not heartbeat. Direct course entry is reflected by the course's authenticated progress API request, not by every JS/image fetch.
- The current account card shows `ใช้งานอยู่ตอนนี้` for the current request. Other cards show their last recorded activity (minute precision, not a live online indicator). Relative Thai text advances locally every 30 seconds from server time using a monotonic browser clock, without polling or writing activity. Reload fetches fresh activity. Exact ISO UTC timestamps remain in `<time datetime>`, accessible labels and/or title; joined dates are formatted in Thai using UTC.
- `/members/<integer-id>` is linked from leaderboard rows and uses the same card. Authentication is required; missing IDs return 404. Other members see name/handle/bio/photo/level/joined/activity, **not emails or edit/upload controls**. No unauthenticated public profile exposure. There are no followers, following, social features, contribution counts or fictional metrics.

## Level ring
`achievements.level_progress` uses the existing `THRESHOLDS`, `level_for`, and full-course completion source. No duplicate threshold table and no points. L1→L2 is 0/1 course. L2–L7 rings reset at each threshold and show `(completed - current threshold)/(next threshold - current threshold)`, with the remaining **whole courses** in the caption. Help explains one CLASS means every current lesson in one enabled/built valid course. L8 is an unfilled **exam pending** ring, not a score, with ≥95% requirement and no fictional next-course target. L9 is a full ring and congratulations, permanent even if curriculum changes. Accessible progressbar values and caption match the visual ring; zero progress is intentionally gray rather than a false blue arc.

## Interface and privacy
- `GET /account/profile`: read-only own-account Thai profile card. Accessible file label/help, local preview and upload/remove forms live only in `/account/profile/edit`. Header avatar links here; images/initials are shared across catalog, profile, exam header, leaderboard summary and rows.
- `POST /account/profile`: session-derived owner only; no user ID or external URL accepted. Multipart fields are `csrf_token`, optional `action=upload`, and exactly one `photo`. Removal uses `csrf_token` and `action=remove`, no file. Duplicate/unknown fields are rejected. Successful photo write redirects 303 to `/account/profile/edit?photo_saved=1`; invalid images return the editor with Thai 400; oversized bodies/files return the editor with Thai 413. The POST URL is retained for compatibility. Photo errors preserve stored identity and the existing photo; text-validation errors retain submitted text values. These are independent forms: save text edits before submitting a photo. Rejected oversized bodies are not parsed again, and cannot recover unsent/rejected text. Removal still requires an explicit CSRF-protected POST action.
- Existing session-bound CSRF plus Origin and Sec-Fetch-Site protections apply before writes. All other endpoints retain the existing 16 KiB body limit. Only authenticated POST to this exact upload endpoint permits 5 MiB + 16 KiB multipart overhead; parser has four-part and 80 KiB memory limits. The actual file is independently limited to 5,242,880 bytes.
- `GET /account/photos/<integer-user-id>` serves only the current processed JPEG by DB lookup, requires authentication, and has `Cache-Control: no-store`, `nosniff`. Logged-in members may see each other's photos (same privacy as leaderboards); guests redirect to login. Missing photo is 404. No arbitrary filename or directory serving, no external image URLs, no originals.

## Validation / processing
Pillow 12.3.0 (pinned in appworks requirements) detects and fully decodes actual bytes. Extensions and declared MIME do not authorize files. JPEG, PNG, WebP only; GIF/SVG/other formats and multi-frame APNG/WebP rejected. Minimum each side 32 px, maximum each side 4096 px, maximum total 12,000,000 pixels. Pillow decompression bomb warnings/errors fail closed before load; truncated/corrupt images rejected. EXIF orientation is applied, then a fresh white-backed RGB canvas is re-encoded as JPEG quality 85, maximum 256 × 256 with aspect ratio retained. EXIF, comments, text and ICC metadata are not copied. The browser preview is only a convenience, never validation or a saved image; server validation is authoritative.

## Storage / migration
`profiles.install` preserves the nullable `users.photo_ref TEXT` migration alongside the additive profile fields described above. Store only random 48-hex `.jpg` basenames, not user paths. Default directory is `profile-photos` beside the configured SQLite DB (production `appworks/instance/profile-photos`). Override using `APPWORKS_PROFILE_UPLOAD_DIR` or factory config `PROFILE_UPLOAD_DIR`. Keep this private runtime-data directory outside published static/template/course trees; never expose the project/instance root via a static server. Directory creation uses 0700 and exclusive new image creation 0600, no execute bits. Back up both DB and referenced images together.

Image is written first, SQLite reference is changed in an immediate transaction, and only after successful commit is the old unreferenced image cleaned up. Another user's shared reference prevents deletion. Failed DB transaction removes only the newly created image, preserving the old one. Random-name collisions cannot overwrite/delete existing files. Lexically unsafe DB references and symlinks cannot be served/deleted. Process crash between file write/commit or commit/cleanup may leave an orphan thumbnail; no automatic filesystem sweep is performed (safer than guessing ownership). Storage filesystem must remain administrator-owned; no untrusted local writer is in the threat model.

## Operator handoff
Install with `cd appworks && .venv/bin/pip install -r requirements.txt`; Pillow was installed and `pip check` passed. Before production restart, use SQLite backup API and check backup integrity; preserve the existing DB, sessions/progress/exams. The parent/operator owns the existing 8080 process restart. This implementation did not restart it or create production QA accounts/photos. Configure a durable writable private photo directory if overriding the default. Do not point production at evidence QA paths.
