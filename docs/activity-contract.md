# Activity calendar contract

## Scope and privacy

`/account/profile` and authenticated `/members/<id>` share the same member-scoped 53-week calendar. Editing remains exclusively `/account/profile/edit`. A member can see another member's daily counts by type, not email, course/lesson identifiers, precise event times, URLs, IPs, user agents or session details. There is no client activity endpoint and no arbitrary date/user-ID payload. The existing authentication rate limiter is separate; this feature does not collect IPs.

Activity is evidence of server-observed actions, **not time spent, attendance verification, reading comprehension or exam success**. No streaks or invented history. Exam submission is intentionally not counted in v1.

## Additive migration

`appworks/activity.py:install()` creates, without changing existing account/progress data:

- `activity_tracking(id INTEGER PRIMARY KEY CHECK(id=1), started_at REAL NOT NULL)` — one immutable deployment inception, inserted only if absent.
- `activity_events(user_id, day, kind, subject, observed_at)` — primary key `(user_id,day,kind,subject)`. `kind` is constrained to `login`, `course_open`, `lesson_completed`.

`observed_at` and inception are UTC Unix timestamps generated by the server. `day` is explicitly derived using `ZoneInfo('Asia/Bangkok')`, not the host or browser timezone. The minimal unique facts are retained in SQLite; there is no full clickstream. Subjects are internal dedup keys only and never rendered. There is currently no retention/pruning job; only the rolling calendar is queried/displayed.

Migration neither reads nor backfills `joined_at`, `last_active_at`, old progress or old sessions. Existing manually corrected join timestamps remain unchanged. Before inception: unknown, hatched cells. From inception through today: known recorded activity or no recorded activity. Inception's first local day is explicitly partial. Future cells are blank/disabled. Restart preserves inception and all saved facts. A pre-existing session does not retroactively generate a login event.

## Counting rules

| Kind | Server hook | Deduplication |
|---|---|---|
| Login | Successful credential validation and session issuance, same transaction | One per member/Bangkok day; logout/relogin does not inflate it |
| Course open | Successful HTTP 200 GET of the protected manifest HTML entry, including safe extensionless SPA fallback | One per member/course/Bangkok day |
| Lesson completed | Newly inserted valid `lesson_progress` row, same transaction | Only first-ever completion per member/course/lesson; duplicate requests and next-day retries never add activity |

Course entry HEAD, assets, other HTML files, missing/disabled/unknown courses, failures, redirects, range partial responses, unauthenticated requests and API polling do not count. When browsers supply `Sec-Fetch-Dest`, only `document` counts; absent headers remain compatible with normal HTTP clients. Opening a course measures entry, not proof of studying. Course hooks are generic: no Scale Lab branch and no frontend instrumentation is required.

Progress validation, session ownership, CSRF and Origin checks stay in force. Course/lesson subjects come from validated server manifests. Login and progress events commit with the underlying change. Unique SQLite keys serialize concurrent retries. Existing `last_active_at` heartbeat is unchanged and intentionally broader than calendar activity.

## Calendar and accessibility

53 complete Monday–Sunday columns, current week last, with month labels at the week containing the month's first day. Today uses Bangkok's date. Summary: days with any activity and days with course-open/completion in the last 30 local days, inclusive of today. Login alone is not a learning day.

Green levels by total recorded actions: **0 / 1–2 / 3–4 / 5–7 / 8+**. Thai “น้อย → มาก” legend and “นับอย่างไร” explanation make the thresholds explicit. Dots indicate active cells without relying solely on color. Each day is a real button with date/type-count accessible name and `aria-pressed`; click or Enter/Space updates a visible live daily-details panel. Unknown-day details explain missing historical observation rather than asserting inactivity. Narrow screens stack below the profile; only the calendar scrolls horizontally. No page overflow at 320/390px in actual Chromium QA.

## Deployment and verification

Back up the production SQLite via its backup API and preserve uploads first. The owning operator must restart the existing 8080 backend to load Python and templates together. Inception begins on this first upgraded startup, not the development/QA date. No production DB was opened by the feature's QA servers; no user join timestamp was edited. No new third-party dependencies.

QA: `appworks/.venv/bin/python scripts/activity-qa-server.py` binds 8099 with separate SQLite, private photo directory and copied course fixtures. `node scripts/activity-browser-verify.mjs` exercises real UI. To verify a genuine process restart, stop only that QA PID, restart with `--reuse evidence/activity-qa-<suffix>`, then run `node scripts/activity-restart-browser.mjs`. Reuse refuses paths outside the isolated QA directory naming/location. Never run fixture scripts against production. See [verification evidence](../evidence/activity-verification.md).
